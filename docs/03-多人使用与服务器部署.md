# 多人使用与服务器部署

目标：用户通过固定 HTTPS 网址打开工作台，自行注册账号，独立保存目标、任务、图片和周报。服务器持续运行，访问不依赖开发者电脑开机。

## 1. 本次采用的部署方式

一台 Linux 服务器运行三个容器：Caddy 提供 HTTPS 与网页，Java 后端处理业务，MySQL 保存数据。仅 80/443 端口公开；Java 和 MySQL 不映射公网端口。数据库、上传图片、证书分别保存到持久卷。

建议小规模开始：2 核 CPU、4 GB 内存、至少 40 GB SSD、Ubuntu 24.04 LTS，安装 Docker Engine 与 Compose 插件。2 GB 内存需要更谨慎地配置构建和运行资源；本项目尚未提供可承诺的并发容量数据。

Docker 官方安装说明：https://docs.docker.com/engine/install/ubuntu/

## 3. 全新服务器部署

以下步骤用于新建的独立环境。数据库建表仅在空持久卷第一次启动时执行；不要对已有业务库重复导入 `schema.sql`。

1. 将部署包解压到 `/opt/study-cockpit`，或检出经过验证的源码版本。
2. 将自己的域名（例如 `study.example.com`，需替换）解析到服务器公网 IP。
3. 在服务器防火墙和云安全组开放 TCP 80/443；SSH 仅允许管理来源。不要开放 3306/8080。
4. 检查 Docker 与 Compose 已安装，且服务器可以拉取所用镜像。
5. 在项目根目录执行：

```bash
docker version
docker compose version
bash deploy/docker/setup.sh study.example.com
docker compose config --quiet
docker compose up -d --build --wait
docker compose ps
```

`setup.sh` 生成权限 600 的 `.env`，随机生成数据库密码、root 密码、JWT 密钥和图片签名密钥，并设置 `APP_ALLOW_REGISTER=true`。不重复覆盖已有配置。请妥善备份该文件，不上传 GitHub，不发送到聊天或公开日志。

Caddy 会为正确解析且 80/443 可达的公网域名申请并续期 HTTPS 证书。证书依赖域名解析和外部签发服务；配置文件存在不代表证书已经签发成功。说明：https://caddyserver.com/docs/automatic-https

完成后访问 `https://自己的域名`，点击“创建账号”，注册后返回登录。没有内置管理员密码，也无需把个人账号分享给其他人。

## 4. 注册控制与账号规则

- 用户名为 3–64 位英文字母、数字、下划线、点或短横线。用户名不可重复，数据库默认排序规则不区分大小写。
- 密码至少 8 位，UTF-8 编码长度不超过 72 字节；这是 BCrypt 存储的长度边界。昵称可留空。
- 登录与注册分别按客户端 IP 限流，默认每个接口每分钟 5 次。共享网络下批量注册可能触发限流，稍后可重试。
- 关闭新用户注册时，将 `.env` 中 `APP_ALLOW_REGISTER` 改为 `false`，运行 `docker compose up -d backend`。登录页隐藏注册入口，注册接口也会拒绝新建账号。已有账号可继续登录。
- 当前采用用户名/密码登录，不含微信网页登录、邮箱验证、自助找回密码或管理员网页。忘记密码需由服务器维护者核实身份后处理。
- 每位用户只能操作自己的数据；上线后应使用两个测试账号验收目标、任务、图片与报表隔离。

## 5. 数据保存、备份与恢复

`db-data` 保存 MySQL 数据，`uploads` 保存学习图片，`caddy-data` 保存证书。容器重新创建不会主动删除这些卷。不要执行 `docker compose down -v`；该命令会删除持久卷。不要在已有数据时重新生成 `.env` 或任意更改 Compose 项目名。

数据库备份：

```bash
cd /opt/study-cockpit
bash deploy/docker/backup.sh
```

备份保存在 `backups/`，该目录不会提交 Git。该脚本校验压缩结果并在成功后发布文件，默认不自动删除历史备份；按实际磁盘容量制定保留策略。可配置 cron 每天执行，并定期复制到另一台设备。图片不包含在 SQL 备份里。

如要完整迁移图片，可先暂停写入并导出：

```bash
docker compose stop backend
mkdir -p backups
umask 077
docker compose run --rm --no-deps --entrypoint tar backend \
  -C /data/study-cockpit/uploads -czf - . > backups/uploads.tar.gz
docker compose start backend
```

恢复时先在空的独立测试库验证备份，确认后再安排业务停机。以下命令仅在独立测试部署中执行，导入会创建备份中的表：

```bash
gzip -t backups/实际备份文件.sql.gz
gzip -dc backups/实际备份文件.sql.gz | docker compose exec -T db \
  sh -c 'MYSQL_PWD="$MYSQL_ROOT_PASSWORD" exec mysql -u root study_cockpit'
```

如果原库已有表，应先制定替换与回滚步骤，不要直接把上面的命令指向生产业务库。

## 6. 更新、验收与故障定位

更新前备份数据库，保留原代码版本和 `.env`，然后构建并替换容器：

```bash
docker compose up -d --build --wait
docker compose ps
docker compose logs --tail=100 backend web
```

上线验收：HTTPS 证书受浏览器信任；注册、登录、改密和退出可用；两个账号的数据隔离；图片可上传查看；重启容器后账号和任务保留；备份可在独立库恢复。

仓库 CI 会构建三个服务并以临时的本地 CA 检查 HTTPS、注册、Cookie、账号隔离和备份。该检查验证部署配置，不能代替实际服务器的公网 DNS、证书签发、网络可达性和容量测试。

`deploy/docker/smoke-test.py` 仅适用于 CI 或专用测试部署：它会创建测试账号与测试数据。不要直接对公开生产网址执行。

原有手动 Nginx/systemd 部署方式见 `02-部署文档.md`。两种方案择一使用，避免同时占用 80/443 端口。
